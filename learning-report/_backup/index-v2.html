方法论认知框架

四套方法论覆盖了 AI 编程协作的不同层面：MCP 是「接入层」标准，BMAD 是「角色层」范式，GSD 是「流程层」引擎，SDD 是「质量层」保障。它们回答的不是同一个问题，而是可以叠加使用的四层。

方法论核心思想解决什么问题关键机制代表笔记
MCP 把「AI 连接数据源与工具」标准化 AI 应用如何即插即用地接入外部能力 五类原语：Resource / Prompts / Tools / Sampling / Roots；stdio 传输；JSON-RPC 2.0 agent.md
BMAD 给 AI 一个「人设」，按专业角色协作 让 AI 在不同阶段以对应专家身份产出 命名智能体 + customize.toml 人设 + 菜单分发 + 官方/团队/个人三级覆盖合并 BMAD.md
GSD 工作流 + 子 Agent + 上下文管理 长任务中防止上下文腐化、控制 token 层级路由（6 命名空间）；section_manifest 条件加载；子 Agent 隔离上下文；跨运行时适配；hook 系统 gsd.md / new-project.md
SDD / OpenSpec 先定义规则，再实施实现 复杂需求如何避免 AI 越权、保持文档与代码一致 propose → apply → sync → archive 四步闭环；底层+上层双层 Skill；AGENTS.md 入场说明书；Hooks 强验证 SDD学习.md

贯穿四套方法论的共同命题是上下文管理：所有框架都在用「少加载、按需读、隔离执行、沉淀复用」的方式，控制 token 开销并延长单次会话的有效记忆。这也是后续自建 Skill 时最值得复用的设计思想。

核心成果详解：4 个 Skills + 1 个 Agent

这是全仓库含金量最高的部分——把第二阶段的方法论认知真正做成了可复用资产。每个技能都遵循「规则文件 + 工作流 + 评测样例」的结构，并配套自研工具与测试。

api-rules Skill
定位：后端 API 设计统一规范，拒绝小项目常见的 {code, message, data} 三字段套路，理由是它重复 HTTP 语义、无法承载分页/追踪/版本化。
  • 信封最小化：成功 {data}，分页加 {meta}，失败 {error}
  • 结构化错误：code 用机器可读字符串，details 仅在有字段校验错误时出现
  • 约定：RESTful /api/v1、camelCase、ISO 8601、Bearer Token、pageSize≤100
  • 分层：DTO 何时省略有明确判断标准；DDD 调用链按复杂度切换
  • 共享：ApiResponse/Meta/ErrorCode 集中在 common 模块，禁止各模块复制
371 行 · 附 Java 代码示例 + evals 评测
moni-app-skill Skill
定位：Android 应用构建规范，强制 Kotlin + Jetpack Compose + MVVM。
  • 架构：每屏 Screen/ViewModel/UiState 三件套，ViewModel 不碰 View
  • 主题：颜色/字号/尺寸全部参数化，禁硬编码
  • 日志：先跑 scan_logging_utils.js 检测项目是否已有日志工具，有则只用它，无则不引入官方 Log
  • 范围：只建用户要求的文件，杜绝「顺手添加」的测试与辅助类
SKILL 80 行 + scan_logging_utils.js 111 行 + test 109 行 + evals
profession-commentor Skill
定位：Java 中文 Javadoc 注释规范，核心理念「代码讲 what/how，注释讲 why」。
  • 分元素规则：类/接口带 @author moni；方法带 @param/@return/@throws；DTO record 逐字段 @param
  • 克制原则：字段名自明则不注释；简单逻辑不注释；复杂逻辑只解释原因
  • 反例教学：「// 创建用户」这类废话注释被明确列为反面示例
190 行 + evals + 3 个 Java 评测样例（34/52/30 行）
writeself_app_style_rules Skill
定位：WriteSelf 产品设计系统，规模最大的技能，由 6 个独立规则文件构成。
  • 文件分工：rules（视觉/字型）/ color_rules（颜色体系）/ page_composing_rules（页面构成）/ shared_page_composition_rules（跨页间距）/ components_styles（组件样式）/ component_semantics（信息-组件语义映射）
  • 流程：9 步审计流程，每步指向具体规则文件章节，逐条可溯源 [Source: 文件 §节]
  • 样例：15 个违规案例 + 修正方案（含设计系统内部冲突的裁决规则）
  • 进阶处理：暗黑模式缺失、RTL 未支持等按 INFO 级提示，不擅自发明色值
937 行 · SKILL 144 + 6 规则文件 717 + 中文版 76

不足与改进建议

以下问题按严重程度排序，每条给出具体证据、影响与可执行建议。

高

知识无索引，缺乏导航

证据：README.md 仅 2 行（「记录前端自救之路」）；11 篇笔记平铺在根目录，无目录、无知识地图、无优先级标注。

影响：新读者与未来的自己都无法快速定位；笔记之间的关联（如 gsd.md 与 new-project.md 的从属关系）只能靠人工推断。

建议：重写 README 为知识地图，按「环境/方法论/实践」三类索引全部文件并附一句话摘要；每篇笔记顶部补一行摘要与状态标记。
高

明文敏感凭据入库

证据：后端项目.md 中完整记录了 Maven 私服账号与密码。

影响：凭据随 Git 仓库扩散，一旦仓库被推送至远程或分享，凭据即泄露；历史提交中的凭据无法通过删除文件清除。

建议：立即从文档移除真实凭据，改用环境变量或本地 settings.xml 引用；评估是否重置私服密码，并检查仓库是否有远程推送历史。
中

笔记消化不彻底，疑问未回填

证据：new-project.md 保留大量「?:」标记，其中部分疑问（如 execution_context 的来源）在 gsd.md 已解答，但原笔记未回填；两份文档对同一机制描述重复且口径不一。

影响：同一主题存在两个版本，未来引用时容易以错为准；未解答疑问随时间丢失上下文。

建议：以 gsd.md 为准合并去重；已解答疑问回填结论，未解答的集中到一个「待研究清单.md」持续维护。
中

技能与学习仓库职责混杂、路径硬编码

证据：4 个产品级 Skills 存放在学习仓库；writeself_app_style_rules/SKILL.md 硬编码绝对路径 d:\myAgentStudyApproach\skills\writeself_app_style_rules\。

影响：换机、迁移或分享仓库后技能立即失效；技能本应服务具体产品项目（如 WriteSelf），却被「藏」在学习仓库里难以被其他项目发现。

建议：将成熟技能迁移到全局技能目录或独立仓库；SKILL.md 内路径改用 {skill-root} 相对引用；学习仓库保留笔记与说明。
中

存在空文件与未完成项

证据：主agent和子agent之间的通信.md 为 0 行（标题已立、内容未写）；ponytail.md 仅 1 行链接；tuide_tools_prompt.md 只有需求文档、无实现代码。

影响：占位文件造成「已完成」的错觉；通信机制恰是 GSD 研究的核心收获，缺这篇等于最值得沉淀的知识没有沉淀。

建议：优先补写通信机制笔记（可直接取材 gsd.md 的子 Agent 章节）；未完成项标注 TODO 状态或移出仓库。
低

验证覆盖有限，缺少阶段复盘

证据：各 Skill 的 evals 仅 20+ 行、覆盖 1-3 个样例；scan_logging_utils.js 的测试是否持续运行无记录；仓库没有任何总结性文档。

影响：技能在边界场景（异常输入、极端参数）的行为未被验证；学习过程没有里程碑，无法回答「这三个月到底收获了什么」。

建议：扩充 evals 用例（含反例与边界）；记录测试执行结果；以本报告为起点建立定期复盘机制。
低

笔记以转述为主，原创分析占比偏低

证据：SDD学习.md 后半段基本为官方文档转述；多篇笔记以「记录要点」为主，「我的判断」类段落较少。

影响：转述易随时间贬值，判断与对比才构成个人知识资产；gsd.md 中「与 BMAD 的对比」就是好的示范，但数量太少。

建议：每篇笔记补一段「我的结论」——它解决什么问题、与什么冲突、我会怎么用；不必长，一段即可。

总体评价

这是一份质量被低估的学习档案。投入集中在 GSD / BMAD 等框架的源码级研究上，且没有停留在「看懂」，而是亲手产出了 4 个带评测的技能与 1 个自定义智能体，形成了「输入 → 消化 → 产出」的完整闭环。工程习惯（git 规范提交、工具自测、双语文档、提问式学习）也相当扎实，超出了普通学习笔记的水平。

主要短板不在学习本身，而在知识的组织与收尾：缺导航、有凭据、有未完成项、转述多判断少。补齐这些，仓库就能从「学习草稿箱」升级为「可复用资产库」——而前五项建议的改动量其实很小。
