<purpose>
准确理解用户需求。
</purpose>

<principles>
- 只执行当前文件中规定的内容，不擅自执行其他文件、技能或流程中的内容，除了`interview-me`和`interview-me`中要求的文件活内容。
- 用户说"简单做"就别追问边界条件，先做完再问。
- 每次只聚焦一个问题领域，不要发散。
- 用业务语言，别用技术术语解释用户的需求。
- 不确定时直接问，不要猜。
- 只有用户确认理解正确后，才能进入后续阶段。
- 不得在对话框中直接输出完整需求文档，以免浪费 token；最终需求文档应保存到文件中。
</principles>

<steps>

### 1. 询问需求文档

```json
{
  question: "你是否有需求文档？",
  header: "需求来源",
  options: [
    { label: "有", description: "提供需求文档路径或链接" },
    { label: "没有", description: "通过其他方式提供需求" },
    { label: "跳过：执行脚本", description: "暂未实现" }
  ]
}
```

- 选"有" → 进入 2
- 选"没有" → 进入 3

### 2. 获取文档地址

```json
{
  question: "请提供需求文档的路径或链接：",
  header: "文档路径",
  options: [],
  multiple: false
}
```

- 如果用户提供的是本地文件路径：
  - 文件不存在 → 说明“文件不存在，无法读取需求文档”，并提示用户提供正确路径、上传文件，或改为手动输入需求。
  - 文件存在但无法读取（例如权限不足、被锁定、编码异常） → 说明“文件存在但无法读取”，并让用户提供可访问版本或直接输入需求描述。
- 如果用户提供的是链接：
  - 链接不可访问（404、403、超时、跳转失败） → 说明“链接无法访问，无法读取需求内容”，并要求用户提供可访问的链接、截图、文档内容或改用手动输入。
  - 链接可访问但内容无法解析或为空 → 说明“链接内容为空或无法解析”，并要求用户重新提供有效文档或直接描述需求。
- 只有在路径/链接可访问且内容可读取时，才继续读取文档内容。
- 读取文档内容后 → 进入 5

### 3. 选择输入方式

```json
{
  question: "如何提供需求？",
  header: "输入方式",
  options: [
    { label: "自己输入", description: "直接描述你的需求" },
    { label: "深度提问", description: "由 AI 通过 interview-me 技能引导挖掘真实需求" }
  ]
}
```

- 选"自己输入" → 进入 4
- 选"深度提问" → 加载 `interview-me` 技能与用户对话

### 4. 接收用户输入

用户自行描述需求。拿到需求描述后，进入 5。


### 5. 理解—反馈—修正—确认闭环

第 5 步不是一次性的确认节点，而是可以反复迭代的需求理解闭环。每轮都必须先整理当前理解，再让用户反馈；如果用户反馈不正确或需要补充，则根据反馈修正理解并重新确认，直到用户确认正确。

#### 5.a 理解

基于需求文档或用户输入，整理当前对需求的理解：

> 总结以上，我理解的需求是：[我的理解]。是否有遗漏或需要调整的地方？

#### 5.b 反馈

使用 `question` 工具让用户反馈当前理解是否正确：

```json
{
  question: "是否理解正确？如果不正确，请说明需要补充或修改的内容。",
  header: "需求确认",
  options: [
    { label: "正确", description: "当前需求理解准确，可以结束本轮确认" },
    { label: "不正确", description: "需求理解有遗漏或错误，需要补充反馈" }
  ],
  multiple: false,
  additionalProperties: false
}
```

#### 5.c 修正

- 用户选择“不正确”：

1. 不得清空或重新开始已有的需求理解。
2. 保留原始需求、已确认的信息和此前的交流上下文。
3. 根据用户指出的偏差，修正当前需求理解。
4. 如果用户未明确指出偏差，先询问具体不正确的内容。
5. 修正时检查相关需求是否受到影响，不得自行补充未经确认的业务规则。
6. 如果仍存在影响需求理解的疑问，继续与用户交流，直到疑问得到解决。
7.用户明确要求停止或跳过时，保留待定状态；不得伪装成已经确认。
8. 每次修正后，进入5.a。


#### 5.d 确认

- 用户选择“正确”，则结束需求挖掘闭环，输出最终确认后的需求理解，进入后续流程。

### 6. 输出需求到文档

- 将最终需求文档写入用户指定的文件路径，不要把完整文档内容粘贴到对话框中。
- 如果目标文件已存在，先询问用户是否覆盖。
- 如果无法写入文件，说明原因并询问用户下一步如何处理，不得改为在对话框中输出完整文档。


</steps>
