<purpose>
准确理解用户需求。
</purpose>

<principles>
- 只执行当前文件中规定的内容，不擅自执行其他文件、技能或流程中的内容；`interview-me` 是本流程明确授权的技能，仅在用户主动选择“深度提问”后调用。
- 用户说"简单做"就别追问边界条件，先做完再问。
- 每次只聚焦一个问题领域，不要发散。
- 用业务语言，别用技术术语解释用户的需求。
- 不确定时直接问，不要猜。
- 只有用户确认当前需求理解正确后，才能进入需求完整性检查；只有影响需求理解的关键问题得到解决后，才能将需求标记为已完成确认。
- 不得在对话框中直接输出完整需求文档，以免浪费 token；最终需求文档应保存到文件中。
- 对于已确认信息、待确认信息和待定事项必须明确区分，不得把 AI 自行推断的内容标记为已确认。
- 文件读取、存在性检查、写入和覆盖操作必须通过当前环境实际可用的工具完成。不得仅根据模型生成的内容推断文件存在、已写入或已保存；如果当前环境不具备所需文件操作能力，必须说明具体受限环节，不得伪造操作结果。
</principles>

<configuration>
- 需求文档模板：当前技能目录下的 `templates/requirement-output.md`。
- 默认输出路径：未配置。未配置时询问用户目标文件路径，不得自行选择目录。
</configuration>

<steps>

### 1. 询问需求文档

以下为交互意图示例，不是通用工具调用格式；实际调用时按当前环境中可用的提问工具及其参数定义执行。

```text
{
  question: "你是否有需求文档？",
  header: "需求来源",
  options: [
    { label: "有", description: "提供需求文档路径或链接" },
    { label: "没有", description: "通过其他方式提供需求" }
  ]
}
```

- 选"有" → 进入 2
- 选"没有" → 进入 3

### 2. 获取文档地址

```text
{
  question: "请提供需求文档的路径或链接：",
  header: "文档路径",
  options: [],
  multiple: false
}
```

- 如果用户提供的是本地文件路径：
  - 文件不存在 → 说明“文件不存在，无法读取需求文档”，并提示用户提供正确路径、上传文件，或改为手动输入需求。
  - 文件存在但无法读取（例如权限不足、被锁定、编码异常） → 说明“文件存在但无法读取”，并让用户提供可访问版本或直接输入需求描述。
- 如果用户提供的是链接：
  - 链接不可访问（404、403、超时、跳转失败） → 说明“链接无法访问，无法读取需求内容”，并要求用户提供可访问的链接、截图、文档内容或改用手动输入。
  - 链接可访问但内容无法解析或为空 → 说明“链接内容为空或无法解析”，并要求用户重新提供有效文档或直接描述需求。
- 只有在当前环境具备相应访问能力且实际成功读取内容后，才能认定链接可访问并继续。不得仅根据链接格式、页面标题或用户声称链接有效，就认定已获取需求内容。
- 对需要登录、授权或特定客户端才能访问的文档，说明当前访问限制，并请求用户提供当前环境可读取的版本、粘贴文档内容或改为直接描述需求。
- 本地文件同样必须通过当前环境实际可用的工具成功读取；不得根据路径名称或文件类型推测内容。
- 读取文档内容后 → 进入 5

### 3. 选择输入方式

```text
{
  question: "如何提供需求？",
  header: "输入方式",
  options: [
    { label: "自己输入", description: "直接描述你的需求" },
    { label: "深度提问", description: "由 AI 通过 interview-me 技能引导挖掘真实需求" }
  ]
}
```

- 选"自己输入" → 进入 4
- 选"深度提问" → 仅在用户明确选择时加载 `interview-me` 技能；加载后继续与用户交流，直到需求可被整理为需求理解。

### 4. 接收用户输入

用户自行描述需求。拿到需求描述后，进入 5。

### 5. 理解—反馈—修正—确认闭环

第 5 步不是一次性的确认节点，而是可以反复迭代的需求理解闭环。每轮都必须先整理当前理解，再让用户反馈；如果用户反馈不正确或需要补充，则根据反馈修正理解并重新确认，直到用户确认正确。

#### 5.a 理解

基于原始需求及此前的交流上下文，整理当前需求理解。

内部持续维护以下信息：
- 已确认信息：用户明确提出或已经认可的需求；如果 AI 对其含义的理解仍有歧义，不得标记为已确认。
- 待确认信息：存在歧义、冲突或尚未得到用户确认的内容。
- 待定事项：不影响当前核心需求理解，但尚未确定的非关键细节。

每轮向用户展示当前需求理解，并重点突出本轮新增、修改或仍需澄清的内容。如果某类信息不存在，不必强行展示该分类。

不得将 AI 自行推断的内容标记为已确认。

#### 5.b 反馈

使用当前环境中可用的提问工具让用户反馈当前理解是否正确。：

```text
{
  question: "是否理解正确？如果不正确，请说明需要补充或修改的内容。",
  header: "需求确认",
  options: [
    { label: "正确", description: "当前需求理解准确，可以结束本轮确认" },
    { label: "不正确", description: "需求理解有遗漏或错误，需要补充反馈" }
  ],
  multiple: false,
}
```



- 用户可以通过自然语言补充、修改或表达暂缓确认的意愿，不必强制归入“正确”或“不正确”：
  - 反馈包含修改内容时，进入 5.c。
  - 用户明确确认当前理解正确时，进入 5.d。
  - 用户表示部分内容尚无法确定时，将相关内容保留为待确认或待定；依据其是否影响核心需求，进入 6 澄清或按非关键待定事项继续。


#### 5.c 修正

- 用户选择“不正确”：

1. 不得清空或重新开始已有的需求理解。
2. 保留原始需求、已确认的信息和此前的交流上下文。
3. 根据用户指出的偏差，修正当前需求理解。
4. 如果用户未明确指出偏差，先询问具体不正确的内容。
```text
{
  question: "是否理解正确？如果不正确，请说明需要补充或修改的内容。",
  header: "需求确认",
  options: [
    { label: "正确", description: "当前需求理解准确，可以结束本轮确认" },
    { label: "不正确", description: "需求理解有遗漏或错误，需要补充反馈" }
  ],
  multiple: false,
}
```
5. 修正时检查相关需求是否受到影响，不得自行补充未经确认的业务规则。
6. 如果仍存在影响需求理解的疑问，继续与用户交流，直到疑问得到解决。
7. 如果用户明确要求暂时停止或跳过，则保留待确认项，不得伪装成已确认。
8. 每次修正后，进入 5.a。

#### 5.d 确认

- 用户选择“正确”后，将当前版本的需求理解标记为“用户已确认”。
- 该确认仅针对当前展示的需求理解版本，不代表需求完整性检查已经通过。
- 进入第 6 步进行完整性检查。
- 未受本次修改影响的已确认信息可以保留，不必要求用户重复确认。

### 6. 检查需求完整性

在进入文档生成前，执行完整性检查，确认当前需求是否已经足够明确，是否存在影响后续开发的关键问题。

检查重点：
- 是否存在会改变需求含义的歧义。
- 是否缺少理解核心功能所必需的信息。
- 是否存在相互矛盾的要求。
- 是否存在未经用户确认的推断。
- 是否存在可能导致后续开发对核心功能产生实质性不同理解的事项。

不要要求所有需求都必须包含完整的异常处理、验收标准或边界规则。只有当缺失信息会影响核心需求的准确理解时，才要求用户澄清；其他未确定事项可以记录在最终文档中。

处理规则：
- 如果没有关键问题：进入 7
- 如果存在关键问题：返回 5，继续与用户沟通并修正需求理解
- 如果只有非关键待定事项：标记为“有待定事项”，允许进入 7，但不能宣称需求已完全确认
- 如果用户明确要求跳过、暂缓或停止澄清：
  - 保留尚未解决的关键问题，并标记为“待确认”。
  - 不得将需求标记为“已确认”或宣称需求完整。
  - 只有用户明确要求生成文档时，才可进入 7 生成阶段性需求文档；阶段性文档仅用于记录，不满足正式需求交接条件。


### 7. 生成需求文档

- 使用配置中指定的 `templates/requirement-output.md` 作为需求输出模板。
- 若用户指定了输出路径，则将文档写入该路径；否则使用配置的默认输出路径。
- 使用当前环境中可用的文件工具实际检查目标路径；如果目标文件已存在，先询问用户是否覆盖，未获同意不得覆盖。
- 通过`write`或者`edit`保存所选文档类型；写入操作结束后，必须按第 8 步重新读取并验证目标文件，不能仅凭写入工具返回成功就认定保存成功。
- 如果仍有关键问题且用户没有明确要求停止，返回第 5 步继续澄清。是否生成阶段性文档与是否满足交接条件是两个独立判断。


### 8. 检查文档并交付

- 使用`read`对目标路径执行实际检查。文档仅在同时满足以下条件时才算有效：
  - 目标文件存在且非空。
  - 内容包含需求输出模板的核心结构，至少包括“需求理解文档”“需求背景与目标”“功能需求”和“最终确认结论”等部分。
  - 文件中有与本次用户需求对应的实际内容，不是只写入了空白模板或仍保留未替换的模板占位符。
  - 文档类型、需求状态、待确认问题和交接结论彼此一致。
- 不要求模板中的每个可选字段都必须填写；未讨论或不适用的部分可按模板规则省略或明确标记。
- 若检查通过，继续完成文档内容校验并交付。
- 若文件不存在或无效，先判断当前工作流中是否仍有需求文档内容可用于恢复：
  - 如果有完整文档内容，使用`write`或者`edit`将该完整内容写入目标路径，然后重新读取并按本步骤完整验证。此恢复写入仍受此前对目标文件的覆盖授权约束；若目标文件原已存在且尚未获覆盖许可，不得覆盖。
  - 如果没有完整文档内容可恢复，不得根据简短确认语、需求摘要或零散片段重建并声称写入成功；明确报告目标文件缺失或无效及具体限制，停止文档交付流程，不得报告保存成功或满足交接条件。
- 恢复写入后仍须验证；若仍不存在或无效，报告写入/验证失败及具体原因并停止，不得反复声称成功或将完整文档改为直接输出在对话框中。
- 按以下顺序检查文档：
  1. 内容忠实于原始需求和用户确认结果，未加入未经确认的推断。
  2. 已确认信息、待确认信息、待定事项及未覆盖内容如实标记。
  3. 模板中的适用字段已填写；不适用或未讨论的内容可省略或明确标记，不得为填满模板而杜撰。
- 如果内容校验发现整理错误或遗漏，修正文档后重新读取并验证；如果问题源于需求本身的歧义、冲突或关键缺失，返回第 5 步澄清，按相应文档类型更新后重新写入和验证。
- 只有确认文档已成功写入后，才能报告保存成功和文档路径。
- 交接结论只反映需求理解的成熟程度，不代表技术方案可行性：
  - 已确认：需求理解已得到用户确认，关键疑问已解决；可以交接。
  - 有待定事项：核心需求已明确，仅有非关键细节未定；可以有条件交接，并列明待定事项。
  - 待确认：核心需求仍存在未解决的歧义、冲突或关键缺失；暂不作为最终需求交接。

</steps>

<output>
最终仅在对话中报告需求理解状态、文件保存路径（仅在文件成功写入后提供）、尚未解决的待定事项，以及是否满足后续开发流程的交接条件。不得直接输出完整需求文档。

本 Skill 仅负责需求获取、理解、澄清、确认和文档整理，不自动进入架构设计、技术选型或代码实现。交接结论仅说明需求理解成熟度，不代表技术方案可行性。
</output>
